# План тестирования Internal Ticket System

## 1. Цель

Проверить, что веб-приложение для работы с внутренними заявками корректно выполняет заявленные бизнес-сценарии, соблюдает ограничения ролей и статусов, а frontend, REST API и база данных согласованно работают как единая система.

## 2. Объект тестирования

Internal Ticket System состоит из:

- frontend-приложения на React и TypeScript;
- REST API на FastAPI;
- слоя хранения данных на SQLAlchemy и SQLite;
- JWT-аутентификации администратора;
- nginx как единой точки входа в Docker-окружении.

## 3. Область тестирования

### Входит в тестирование

- загрузка главной страницы и проверка доступности API;
- вход и выход администратора;
- обработка неверных и пустых учётных данных;
- создание заявки;
- клиентская и серверная валидация полей заявки;
- отображение созданной заявки;
- просмотр подробной информации;
- изменение статуса заявки;
- редактирование заявки и сохранение неизменённых полей;
- запрет редактирования заявки в статусе `done`;
- удаление заявки администратором;
- запрет удаления обычным пользователем;
- запрет удаления заявки в статусе `done`;
- поиск по заголовку и описанию;
- фильтрация по статусу и приоритету;
- одновременное применение нескольких фильтров;
- сортировка по дате создания, статусу и приоритету;
- быстрые фильтры;
- сброс обычных и быстрых фильтров;
- пагинация и изменение количества записей на странице;
- состояние пустой поисковой выдачи;
- базовая проверка семантики и доступности интерактивных элементов;
- корректность основных HTTP-статусов и тел ответов API.

### Не входит в текущий объём

- нагрузочное и стресс-тестирование;
- тестирование безопасности и penetration testing;
- проверка работы в кластере или микросервисной инфраструктуре;
- тестирование миграции с других СУБД;
- полноценный аудит WCAG;
- поддержка мобильных приложений;
- полная кросс-браузерная матрица в CI;
- тестирование восстановления после отказа инфраструктуры.

## 4. Виды и уровни тестирования

### Ручное тестирование

- функциональное;
- исследовательское;
- проверка бизнес-правил;
- негативное тестирование;
- проверка граничных значений;
- базовая проверка интерфейса и доступности;
- локализация и документирование дефектов.

### Автоматизированное тестирование API

API-тесты выполняются через pytest и HTTPX против экземпляра FastAPI в процессе тестов. Используется отдельная тестовая SQLite-база в памяти.

Проверяются:

- HTTP-статусы;
- схемы и значения ответов;
- валидация входных данных;
- авторизация;
- бизнес-ограничения;
- изменение состояния данных;
- обработка отсутствующих ресурсов.

### Автоматизированное UI/E2E-тестирование

E2E-тесты выполняются через pytest и Playwright против приложения, запущенного в отдельном Docker Compose-проекте.

Проверяются:

- пользовательские сценарии через браузер;
- взаимодействие frontend с реальным API;
- сохранение данных после перезагрузки;
- синхронизация элементов интерфейса;
- права пользователя и администратора;
- состояния модальных окон, таблицы и форм;
- доступные имена и состояния интерактивных элементов.

### Регрессионное и smoke-тестирование

- `smoke` используется для критических сценариев, без которых приложение нельзя считать работоспособным;
- `regression` используется для расширенного набора функциональных и негативных проверок.

## 5. Техники тест-дизайна

- классы эквивалентности;
- анализ граничных значений;
- таблицы решений для ролей, статусов и разрешённых действий;
- переходы состояний заявки: `new` → `in_progress` → `done`;
- позитивное и негативное тестирование;
- попарное сочетание значимых фильтров;
- сценарное тестирование пользовательских потоков.

## 6. Тестовые окружения

### API-тесты

- Python 3.12;
- pytest;
- FastAPI/HTTPX;
- SQLite in-memory;
- изолированная тестовая конфигурация.

### Локальное E2E-окружение

- отдельный Docker Compose-проект `internal-ticket-system-e2e`;
- приложение доступно по адресу `http://localhost:8080`;
- отдельный Docker volume с тестовой SQLite-базой;
- демо-данные отключены;
- Chromium управляется Playwright.

### CI

- GitHub Actions на Ubuntu;
- Python 3.12;
- Node.js 22;
- Chromium;
- последовательность jobs: API-тесты и frontend-проверки, затем E2E;
- публикация Allure results, trace и video как артефактов.

## 7. Тестовые данные

- данные создаются через pytest-фикстуры и фабрики;
- уникальные значения формируются с помощью UUID;
- сложные предусловия подготавливаются через API;
- основной пользовательский сценарий выполняется через UI;
- учётные данные администратора передаются через переменные окружения;
- E2E-данные не записываются в основную базу приложения;
- Docker volume удаляется после выполнения E2E job в CI.

## 8. Критерии начала тестирования

- требования и бизнес-правила доступны и согласованы;
- приложение успешно собирается;
- зависимости установлены;
- миграции применяются без ошибок;
- тестовое окружение доступно;
- настроены тестовые переменные окружения;
- известны валидные учётные данные администратора.

## 9. Критерии завершения тестирования

- API-, frontend- и E2E-проверки успешно проходят в CI;
- критические пользовательские сценарии покрыты smoke-тестами;
- основные бизнес-правила покрыты позитивными и негативными проверками;
- отсутствуют открытые дефекты критической и высокой серьёзности;
- результаты тестирования и диагностические артефакты доступны;
- известные ограничения зафиксированы в документации.

## 10. Критерии приостановки и возобновления

Тестирование приостанавливается, если:

- приложение не запускается;
- недоступны frontend или API;
- миграции не применяются;
- тестовая база не создаётся;
- большая часть тестов блокируется одной инфраструктурной ошибкой.

Тестирование возобновляется после устранения блокирующей причины и успешной проверки smoke-набора.

## 11. Основные риски

| Риск | Влияние | Меры контроля |
|---|---|---|
| Несогласованность frontend и API | Пользовательский сценарий завершается ошибкой | API-тесты и сквозные E2E-сценарии |
| Нарушение правил для статуса `done` | Изменение завершённой заявки | Негативные API- и UI-проверки |
| Ошибка авторизации или проверки роли | Неавторизованное удаление данных | Позитивные и негативные проверки доступа |
| Нестабильные асинхронные UI-операции | Flaky E2E-тесты | Playwright auto-wait и проверки состояния UI |
| Загрязнение тестовой базы | Зависимость тестов от порядка запуска | Отдельная БД, UUID и изоляция выборки |
| Ошибка фильтрации или пагинации | Неверный набор заявок | Изолированные данные и проверки состава таблицы |
| Неготовность Docker-окружения | Ложное падение E2E | Health check с повторными попытками и Docker logs |

## 12. Приоритеты

- **Critical:** запуск приложения, health check, создание и отображение заявки, вход администратора, основные ограничения доступа;
- **High:** изменение статуса, редактирование, удаление, сохранение данных;
- **Medium:** поиск, фильтрация, сортировка, быстрые фильтры, пагинация;
- **Low:** визуальные и малозначимые текстовые несоответствия, не блокирующие работу.

## 13. Отчётность и артефакты

- Allure results с feature, story, title, severity и шагами;
- screenshot страницы при падении E2E-теста;
- Playwright trace и video для неуспешных сценариев;
- Docker logs при падении E2E job;
- GitHub Actions checks для push в `main` и `refactor`, а также для pull request;
- ручные тест-кейсы, checklist и баг-репорты в `docs/qa`.

## 14. Критерии оформления дефекта

Баг-репорт должен содержать:

- идентификатор и краткий заголовок;
- окружение;
- предусловия;
- шаги воспроизведения;
- фактический и ожидаемый результат;
- severity и priority;
- воспроизводимость;
- вложения или диагностические данные;
- статус дефекта.
